# dispoller — проектные решения и риски

Документ-компаньен к [design.md](design.md). Здесь зафиксированы решения по ключевым
местам дизайна (SN-1…SN-18) с рассмотренными альтернативами и реестр рисков
(R-1…R-17). Ссылки из design.md ведут сюда.

---

## Часть 1. Проектные решения (SN)

### SN-1. Точка инкремента `attempts`

**Решение.** Единственная точка инкремента — claim-запрос (атомарно, вместе со сменой
статуса). На финализации — только сравнение: `attempts >= max_attempts ? 'failed' :
'pending'`. Семантика зафиксирована: **`max_attempts` = максимальное число запусков
`Execute`** в штатном цикле claim→Fail (исключение при перехвате зависшей задачи —
SN-16, ограничено бюджетом SN-18).

**Отвергнутые альтернативы.**

1. Инкремент только на ошибке: ломает симметрию — «зависшая» задача (воркер умер) не
   учитывает свою попытку, и упавший на 1-й попытке воркер даст бесконечные ретраи
   без счётчика.
2. Двойной инкремент (на захвате и на ошибке): одна неудачная попытка считается
   дважды — при `max_attempts=3` задача умрёт после 2 реальных запусков
   (захват: 0→1, ошибка: 1→2; захват: 2→3, ошибка: 3≥3 → failed).

### SN-2. API постановки задач

**Решение.** Добавлены `Enqueue` (автономный) и `EnqueueTx` (в транзакции клиента) —
design §6.4.

**Обоснование.** Суть Transactional Outbox — запись задачи **в транзакции бизнес-данных**.
Отдельный `INSERT` вне транзакции клиента — это уже не outbox, а «просто таблица задач»
с окном рассинхрона: коммит бизнеса прошёл, задачу поставить не смогли — письмо
потеряно. Поэтому библиотека предоставляет оба конца — производителя и потребителя.

### SN-3. Пауза между ретраями (backoff)

**Решение.** Колонка `next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT now()` и предикат
`next_attempt_at <= now()` в claim. Backoff считается движком: экспоненциальный,
30s × 2^n с джиттером, cap 15m. Бонус — бесплатный отложенный запуск (`WithRunAt`).

**Отвергнутые альтернативы.**

1. Ретраить сразу (пауза = interval): для задачи, падающей мгновенно (сеть недоступна,
   конфликт), все 3 попытки сгорят за ~3 interval'а — ретраи теряют смысл; при этом
   общий для всех interval нельзя увеличить, не увеличив латентность новых задач.
2. Не ретраить автоматически (только failed): очередь теряет самовосстановление.

### SN-4. Fencing: защита от «потерянного обновления» при финализации

**Сценарий.** Воркер A взял задачу, обработчик работает дольше `execution_timeout`;
lease истёк, воркер B перехватил задачу; затем A завершает `Execute` и делает
безусловный `UPDATE ... SET status='completed' WHERE id=$1` — он **перезапишет состояние
задачи, принадлежащей B**. Аналогичная дыра для Fail. При at-least-once это не
экзотика, а штатный сценарий (задача с таймаутом 30s и медленным SMTP).

**Решение.** Колонка `lease_token UUID`, генерируемая на каждом claim'е;
Complete/Fail/Release условны по токену.

**Отвергнутые альтернативы.**

1. Условная финализация по `attempts` (`WHERE attempts = $n`): закрывает почти всё,
   но не сценарий release→reclaim, когда attempts возвращается к тому же значению
   (release делает −1, повторный claim +1) при обработчике, проигнорировавшем отмену
   ctx и «воскресшем».
2. Колонка `revision INT`: то же самое, что `lease_token`, но менее читаемо.

**Предел гарантии.** Fencing защищает **состояние задачи**, но не сайд-эффекты —
письмо A и письмо B могут уйти оба (см. R-1, SN-15).

### SN-5. Перехват `processing` с `must_be_finished_at IS NULL`

**Решение.** Предикат `NOW() > must_be_finished_at` для строки с `NULL` даёт `NULL` —
строка не выбирается. По протоколу библиотеки `NULL` при `processing` невозможен
(claim всегда ставит дедлайн), но такую строку может вставить человек/pg_restore/другой
сервис. Defensive-ветка `OR must_be_finished_at IS NULL` в claim гарантирует, что такая
строка будет перехвачена. Также добавлен CHECK-контроль длины `task_type`.

**Почему инвариант не оформлен CHECK-ограничением.** `CHECK (status <> 'processing'
OR must_be_finished_at IS NOT NULL)` пресекал бы нарушение в корне, но отклонял бы
запись ровно тех внешних строк, ради которых defensive-ветка существует: вставляющий
`processing`-строку человек/pg_restore/сторонний сервис почти наверняка хочет, чтобы
задача была выполнена, а получил бы отказ записи (или падение restore) и потерянную
работу. Выбрана устойчивость читателя к неидеальным данным: инвариант зафиксирован
комментарием в DDL (design §4), нарушения видны мониторингу «застрявших» (design §10
включает `must_be_finished_at IS NULL`) и самоликвидируются перехватом; поведение
покрыто тестом T-15, сетап которого (прямая вставка такой строки) был бы невозможен
под CHECK.

### SN-6. Сигнатуры `RegisterHandler` и `Start`

**Решение.** `RegisterHandler(taskType string, h JobHandler, opts ...HandlerOption) error`
(+ `WithExecutionTimeout`), `Start(...) error`.

**Обоснование.** `execution_timeout` уникален для каждого task_type — ему нужно место
в API: вариадик-опции, идиоматичный Go, расширяются без ломки. Ошибки конфигурации
(дубль типа, `concurrency < 1`, повторный запуск) при процедурах без возврата ошибки
теряются — они должны всплывать при запуске. Туда же — `Start` движка без единого
зарегистрированного обработчика: `unnest` пустого массива типов не матчит ни одной
строки, и движок молча поллил бы вхолостую, нагружая БД без пользы; это
конфигурационная ошибка, а не штатный режим (регистрация строго до `Start` и так
зафиксирована контрактом, design §6.2–§6.3).

### SN-7. Поведение при панике обработчика

**Решение.** Паника в клиентском `Execute` не должна убивать процесс воркера:
`recover` в обёртке `execute`, паника превращается в ошибку `"handler panic: ..."` →
обычный путь Fail (ретраи/max_attempts). Иначе одна плохая задача останавливает всю
обработку навсегда.

### SN-8. Класс перманентных ошибок

**Решение.** Минимальное расширение контракта: `dispoller.Permanent(err)` → сразу
`failed` без ретраев.

**Обоснование.** «Невалидный payload» успешен не станет никогда — ретраить его значит
потратить 3 запуска и задержать диагностику. Обёртка не меняет контракт для тех, кто
ею не пользуется.

### SN-9. Незарегистрированные `task_type`

**Решение.** Claim фильтрует по списку зарегистрированных типов (`JOIN cfg` по
`unnest($1::text[], …)`, design §5.1); незарегистрированные висят в `pending`, видимы
мониторингом, подхватятся после регистрации обработчика.

**Отвергнутая альтернатива.** Захватывать и фейлить «handler not found»: выжигает
попытки и генерирует шум, при этом после деплоя нового обработчика задача уже мертва.

### SN-10. Хранится только последняя ошибка

**Решение.** v1 хранит последнюю ошибку в `error_message` и счётчик `attempts`; полный
лог попыток — таблица `background.job_attempts`, roadmap v2 (design §12.5). Компромисс
осознан: меньше нагрузка на запись.

### SN-11. Тип идентификатора

**Решение.** `BIGINT GENERATED ALWAYS AS IDENTITY`: вдвое меньше индексы, монотонность
даёт дешёвый приблизительный FIFO (`ORDER BY id`). UUID оправдан при записи с нескольких
несинхронизированных источников — у нас один PG. Смена на UUID в будущем = одна миграция
колонки, API не завязан на тип (`int64` в Go).

### SN-12. Статус: `enum` vs `TEXT + CHECK`

**Решение.** `TEXT + CHECK`: эволюция статусов (`cancelled` в v2) — это
`ALTER TABLE ... DROP/ADD CONSTRAINT`, а не `CREATE TYPE` + переприсвоение колонки.
Миграции у клиента — эволюция должна быть дешёвой и совместимой.

### SN-13. Индексы под поллинг

**Решение.** Два частичных индекса точно под предикаты claim'а (design §4): они (а)
покрывают обе ветки `OR` (планировщик выполнит `BitmapOr`), (б) не содержат миллионы
completed-строк, т.к. частичные. Один составной индекс
`(status, must_be_finished_at)` обе ветки `OR`-предиката не обслуживает и годится лишь
для мониторинга.

### SN-14. Латентность доставки до `interval`

**Решение.** Ticker-поллинг: задача, вставленная сразу после тика, ждёт до `interval`;
уменьшение interval пропорционально увеличивает нагрузку пустых запросов. v1 — ticker
(простота, предсказуемая нагрузка); v2 — сигнал диспетчеру сразу после освобождения
воркера (eager wake-up, design §12.1).

### SN-15. Exactly-once недостижим в принципе

Даже с идеальным fencing сайд-эффекты обработчика (отправка письма, HTTP-вызов) могут
выполниться дважды: lease истёк → перехват → оба обработчика завершились успешно на
своих сайд-эффектах. Это фундаментальное свойство at-least-once систем без бизнес
идемпотентности. Библиотека фиксирует это в контракте (`JobHandler` docstring) и в R-1.
«Точно один раз» можно получить только уровнем выше: уникальный бизнес-ключ отправки,
таблица идемпотентности и т.п.

### SN-16. Перехват зависшей задачи при исчерпанных попытках

**Сценарий.** Ветка B claim'а (design §5.1) перехватывает `processing`-строки с истёкшим
lease и не сверяется с `attempts`: воркер, умерший на последней попытке (Fail некому
выполнить), даёт задаче ещё один запуск — при `max_attempts=3` возможен четвёртый
(воспроизведено на PostgreSQL 18). Повторные аварии воркера дают серийный перезапуск.

**Решение (пересмотрено, итог — SN-18).** Изначально ограничение не вводилось: перехват —
единственный механизм восстановления после аварий, `max_attempts` трактовался как лимит
**штатного цикла** claim→Fail, а превышение покрывалось контрактом идемпотентности
(R-1). Решение пересмотрено: неограниченный серийный перезапуск задачи, роняющей
процесс при каждом выполнении, признан неприемлемым — введён отдельный бюджет
перехватов (колонки `reclaims`/`max_reclaims`, dead-letter прямо в claim). Итоговая
семантика: `max_attempts` остаётся лимитом штатного цикла; единичный запуск сверх
лимита при аварии на последней попытке возможен, но серия перехватов ограничена
бюджетом — суммарный потолок запусков задачи `max_attempts + max_reclaims`.
Альтернативы ниже отвергались в первой редакции (кэп по `attempts`); кэп по отдельному
бюджету, обходящий их возражения, — SN-18.

**Отвергнутые альтернативы.**

1. В claim для ветки B при `attempts >= max_attempts` переводить строку сразу в
   `failed`: жёсткий кэп, но ключевой запрос усложняется разнотипным исходом в одном
   `UPDATE ... RETURNING`, а задача, чей воркер умер до фактического запуска последней
   попытки, лишится её.
2. Фильтр `attempts < max_attempts` в ветке B + отдельный sweeper «stuck-at-max →
   failed»: появляется класс вечно-`processing` строк, требующий отдельной процедуры.

### SN-17. Graceful shutdown: немедленная отмена in-flight обработчиков

**Решение.** При отмене корневого ctx движка in-flight обработчики отменяются немедленно
(их ctx — потомок корневого), задачи возвращаются в очередь через Release без сжигания
попытки; `Start` дожидается только завершения горутин. Финализация при этом идёт с ctx,
отвязанным от корневого (`context.WithoutCancel`) — иначе ретраи финализации при
остановке всегда бесполезны.

**Обоснование.** Простой и предсказуемый жизненный цикл. Цена — снятые задачи
перезапускаются на другом инстансе при каждом деплое; это покрывается контрактом
идемпотентности (R-1) и дешевле, чем «зависший навсегда» обработчик, игнорирующий
отмену.

**Отвергнутая альтернатива.** Grace-период (`WithShutdownGrace`): доработка в пределах
таймера при остановке уменьшает лишние перезапуски, но усложняет жизненный цикл —
roadmap v2 (design §12.10).

### SN-18. Бюджет перехватов: dead-letter для серийных аварий воркера

**Сценарий.** Следствие неотрегулированного SN-16: ветка B перехвата не сверяется ни с
каким счётчиком, и задача, при каждом выполнении роняющая процесс (OOM, ядовитый
payload), перезапускается неограниченно — серийный crash-loop. Терминальный `failed`
недостижим (Fail некому выполнить), цикл останавливается только ручным SQL, а
мониторинг почти не видит разгон: строка «мигает» как застрявшая лишь на ~interval
между истечением lease и повторным claim.

**Решение.** Пара колонок `reclaims` / `max_reclaims` (дефолт 10). Счётчик
инкрементируется **только** перехватами ветки B — штатный цикл claim→Fail и Release его
не касаются (graceful shutdown бюджет не жжёт); пожизненный, без сброса, сброс — только
`Requeue`. Когда бюджет исчерпан, очередной перехват переводит строку в `failed` прямо
в claim, **без запуска обработчика** (dead-letter; NULL `lease_token` в RETURNING —
сигнал движку, design §5.1). Ближайший аналог — `maxReceiveCount → DLQ` в SQS, но наш
вариант мягче: в SQS один счётчик считает все доставки (штатный ретрай после ошибки
жжёт его так же, как краш), у нас два — `attempts` кэпится на Fail, где запуск
действительно был, и жертва-дефект зажат только аварийной веткой. Как и в SQS,
жертва-дефект принят сознательно: «чистая жертва» повторных аварий может попасть в
`failed` без единого запуска — наблюдаемо (`error_message = 'reclaim budget
exhausted'`, алерт design §10) и обратимо (`Requeue`, design §5.7). Worst case —
деплой из одного процесса: яд роняет воркера каждый цикл, и все in-flight сожители жгут
бюджет синхронно, массово попадая в dead-letter на одном пороге (R-17); в
мультипроцессных деплоях соседей дообрабатывают здоровые инстансы.

**Границы гарантии.** Бюджет ограничивает *серию* перехватов, но не первый лишний
запуск: единичный крах на последней попытке всё ещё даёт запуск сверх `max_attempts`
(SN-16). At-least-once действует в пределах обоих бюджетов (design §2). Dead-letter не
инкрементирует `attempts` (запуска не было), но `reclaims` — как обычный перехват:
итоговое значение `max_reclaims + 1`, поэтому признак исчерпания для мониторинга —
пара `status = 'failed'` + `error_message` (строка — контракт мониторинга, константа
`ReclaimBudgetExhaustedMessage`, design §6.4; алерт — design §10), а не значение
счётчика. Dead-letter не голодит очередь: движок немедленно повторяет claim в том же
тике (design §7.2), `SKIP LOCKED` не задерживает остальные строки.

**Отвергнутые альтернативы.**

1. Не ограничивать (исходная редакция SN-16): неограниченный crash-loop ядовитой
   задачи, недостижимый `failed`, невидимость разгона для мониторинга.
2. Кэп по `attempts` в claim (альтернатива 1 SN-16): жертва-дефект на штатных ретраях;
   потеря последней попытки задачей, чей воркер умер до запуска; то же усложнение
   ключевого запроса без смягчения.
3. Фильтр `reclaims < max_reclaims` в ветке B + отдельный sweeper (альтернатива 2
   SN-16): класс вечно-`processing` строк и лишняя движущаяся часть в эксплуатации.
4. Сброс `reclaims` при штатном claim: снимает пожизненный потолок — чередование
   штатных ретраев и аварий даёт неограниченный перезапуск.

## Часть 2. Реестр рисков (R)

| # | Риск | Вер-ть | Последствие | Митигация |
|---|---|---|---|---|
| R-1 | Двойное выполнение сайд-эффектов (at-least-once) | средняя | бизнес-инцидент (двойное письмо/платёж) | контракт идемпотентности обработчика; fencing состояния; примеры в доке; SN-15 |
| R-2 | Обработчик дольше `execution_timeout` → параллельный перехват | средняя | дубль + лишняя нагрузка | локальный `WithTimeout` на попытку; документация «таймаут = верхняя граница времени попытки»; v2 — heartbeat |
| R-3 | Некорректное использование библиотеки: обработчик игнорирует отмену ctx; `RegisterHandler` из горутины параллельно со `Start` | низкая | «зомби»-обработчик дорабатывает после снятия (утечка горутин, параллельный перехват); гонка на map хендлеров — паника/UB | контракт в godoc: обработчик обязан уважать ctx, регистрация строго до Start; при Start map хендлеров замораживается копией; fencing не даст зомби испортить состояние задачи |
| R-4 | Рассинхрон часов инстансов | низкая | ложные истечения lease | все временные решения в SQL через `now()` БД; app-часы только для локального таймаута (джиттер ± секунды некритичен) |
| R-5 | Поллинг нагружает OLTP-базу; БД — единая точка отказа очереди | низкая (1 запрос/interval/инстанс) | деградация основного трафика | два крошечных частичных индекса; мониторинг `pg_stat_statements`; interval — настройка; отдельная реплика не подходит (нужна запись) |
