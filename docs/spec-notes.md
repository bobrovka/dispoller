# Разбор ТЗ: сомнительные места, отклонения, риски

Документ-компаньен к [design.md](design.md). Здесь зафиксировано всё, что в `task.md`
показалось противоречивым, недоопределённым или рискованным, с вариантами и принятыми
рекомендациями. Ссылки из design.md ведут сюда.

Обозначения статуса:

- ✅ **принято** — решение зафиксировано в design.md, ТЗ не меняется по сути;
- 🔧 **отклонение** — решение меняет что-то явно прописанное в ТЗ (схема, сигнатуры) —
  желательно подтверждение владельца ТЗ;
- ❓ **открытый вопрос** — реализацию не блокирует, но требует решения.

## Часть 1. Сомнительные места ТЗ (SN)

### SN-1. Двойной инкремент `attempts` — противоречие п.4 и п.5 🔧

**Суть.** П.4 ТЗ: при захвате «`attempts` увеличиваться на 1». П.5: «Если `Execute`
вернул ошибку: увеличиваем `attempts`». Если делать и то и другое, одна неудачная
попытка считается дважды: при `max_attempts=3` задача умрёт после 2 реальных запусков
(захват: 0→1, ошибка: 1→2; захват: 2→3, ошибка: 3≥3 → failed). Почти наверняка это
недосмотр, а не намерение.

**Варианты.**
1. Инкремент на claim, на ошибке — только сравнение (скан транзакций River, gue).
2. Инкремент только на ошибке: ломает симметрию — «зависшая» задача (воркер умер) не
   учитывает свою попытку, и упавший на 1-й попытке воркер даст бесконечные ретраи
   без счётчика.
3. Двойной инкремент как в ТЗ: см. выше, семантика `max_attempts` ломается.

**Решение.** Вариант 1: единственная точка инкремента — claim-запрос (атомарно, там же
где и смена статуса). На ошибке только `attempts >= max_attempts ? failed : pending`.
Семантика зафиксирована: **`max_attempts` = максимальное число запусков `Execute`**.

### SN-2. В ТЗ нет API постановки задач 🔧

**Суть.** ТЗ описывает потребителя (воркеры), но не производителя. При этом сам ТЗ
называет паттерн Transactional Outbox, суть которого — запись задачи **в транзакции
бизнес-данных**. Без API `EnqueueTx(ctx, tx, ...)` паттерн не реализуем: отдельный
`INSERT` вне транзакции клиента — это уже не outbox, а «просто таблица задач» с окном
рассинхрона (коммит бизнеса прошёл, задачу поставить не смогли — письмо потеряно).

**Решение.** Добавлены `Enqueue` (автономный) и `EnqueueTx` (в транзакции клиента)
— design §6.4. Это дополнение API-поверхности за рамки буквального ТЗ, но без него
библиотека не решает заявленную задачу.

### SN-3. Нет паузы между ретраями (backoff) 🔧

**Суть.** По ТЗ провалившаяся задача возвращается в `pending` и доступна **на
следующем же тике поллинга**. Для задачи, падающей мгновенно (сеть недоступна,
конфликт), все 3 попытки сгорят за ~3 interval'а — ретраи теряют смысл. В схеме ТЗ
нет колонки для хранения времени следующей попытки.

**Варианты.**
1. Добавить колонку `next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT now()` и предикат
   `next_attempt_at <= now()` в claim. Backoff считается движком.
2. Оставить схему ТЗ, ретраить сразу (тогда interval и есть фактическая пауза — но
   один общий для всех, включая свежие задачи, и его нельзя увеличить, не увеличив
   латентность новых задач).
3. Не ретраить автоматически (только failed) — противоречит п.5 ТЗ.

**Решение.** Вариант 1: экспоненциальный backoff с джиттером (30s × 2^n, cap 15m),
бонус — бесплатный отложенный запуск (`WithRunAt`). Отклонение от схемы ТЗ; строгий
вариант — design, Приложение A.

### SN-4. Нет защиты от «потерянного обновления» при финализации 🔧

**Суть.** Сценарий: воркер A взял задачу, обработчик работает дольше
`execution_timeout`; lease истёк, воркер B перехватил задачу; затем A завершает
`Execute` и делает безусловный `UPDATE ... SET status='completed' WHERE id=$1` —
он **перезапишет состояние задачи, принадлежащей B**. Аналогичная дыра для Fail.
ТЗ этот случай не рассматривает, а при `at-least-once` он не экзотика, а штатный
сценарий (задача с таймаутом 30s и медленным SMTP).

**Варианты.**
1. Условная финализация по `attempts` (`WHERE attempts = $n`): закрывает почти всё,
   но не сценарий release→reclaim, когда attempts возвращается к тому же значению
   (release делает −1, повторный claim +1) при обработчике, проигнорировавшем отмену
   ctx и «воскресшем».
2. Колонка `lease_token UUID`, генерируемая на каждом claim'е; Complete/Fail/Release
   условны по токену. Полный fencing, стоимость — одна UUID-колонка и генерация токена
   на захвате.
3. Полная версия-колонка `revision INT` — то же самое, что 2, но менее читаемо.

**Решение.** Вариант 2 (`lease_token`). Важно понимать его предел: fencing защищает
**состояние задачи**, но не сайд-эффекты — письмо A и письмо B могут уйти оба
(см. R-1, SN-15).

### SN-5. `processing` с `must_be_finished_at IS NULL` недоступна для перехвата ❓→✅

**Суть.** Предикат ТЗ `NOW() > must_be_finished_at` для строки с `NULL` даёт `NULL` →
строка не выбирается. По протоколу библиотеки `NULL` при `processing` невозможен
(claim всегда ставит дедлайн), но строки может вставить человек/рестор/другой сервис.
Defensive-решение: ветка `OR must_be_finished_at IS NULL` в claim — такая строка будет
перехвачена. Также добавлен CHECK-контроль длин `task_type`.

### SN-6. Сигнатуры `RegisterHandler` / `Start` из ТЗ недостаточны 🔧

**Суть.** ТЗ: `RegisterHandler(taskType, handler)` и `Start(ctx, interval, concurrency)`.
Но по п.4 у `execution_timeout` «для каждого task_type свой» — в сигнатуру его класть
некуда. А ошибки конфигурации (дубль типа, `concurrency < 1`) при процедурах без
возврата ошибки теряются.

**Решение.** `RegisterHandler(taskType string, h JobHandler, opts ...HandlerOption) error`
(+ `WithExecutionTimeout`), `Start(...) error`. Функциональные опции — идиоматичный Go,
расширяется без ломки API.

### SN-7. Поведение при панике обработчика не определено ✅

Паника в клиентском `Execute` не должна убивать процесс воркера: `recover` в обёртке
`execute`, паника превращается в ошибку `"handler panic: ..."` → обычный путь Fail
(ретраи/max_attempts). Иначе одна плохая задача останавливает всю обработку навсегда.

### SN-8. Нет класса перманентных ошибок ❓

**Суть.** По ТЗ ретраится любая ошибка. Но «невалидный payload» успешен не станет
никогда — это 3 бессмысленных запуска и задержка диагностики.

**Решение.** Минимальное расширение: `dispoller.Permanent(err)` → сразу `failed`
без ретраев. Не меняет контракт для тех, кто им не пользуется. Если владелец ТЗ
категорически против — выкидывается безболезненно (одна ветка в `run`).

### SN-9. Политика для незарегистрированных `task_type` не определена ✅

**Суть.** Варианты: (а) не захватывать такие задачи; (б) захватывать и фейлить
«handler not found». Вариант (б) выжигает попытки и генерирует шум, при этом после
деплоя нового обработчика задача уже мертва.

**Решение.** (а): claim фильтрует по списку зарегистрированных типов
(`task_type = ANY($1)`); незарегистрированные висят в `pending`, видимы мониторингом,
подхватятся после регистрации обработчика.

### SN-10. Хранится только последняя ошибка ✅ (компромисс, v2 — аудит)

ТЗ не требует истории попыток. v1 хранит последнюю ошибку и счётчик; таблица
`background.job_attempts` — roadmap v2 (design §12.5). Компромисс осознан: меньше
нагрузки на запись.

### SN-11. `id: UUID или BIGSERIAL` — ТЗ оставляет выбор ✅

Принят `BIGINT GENERATED ALWAYS AS IDENTITY`: вдвое меньше индексы, монотонность
даёт дешёвый приблизительный FIFO (`ORDER BY id`). UUID оправдан при записи из
нескольких несинхронизированных источников — у нас один PG. Смена на UUID в будущем =
одна миграция колонки, API не завязан на тип (`int64` в Go).

### SN-12. Статус: `enum` vs `TEXT + CHECK` ✅

`TEXT + CHECK`: эволюция статусов (`cancelled` в v2) — `ALTER TABLE ... DROP/ADD
CONSTRAINT`, а не `CREATE TYPE` + переприсвоение колонки. Миграции у клиента —
эволюция должна быть дешёвой и совместимой.

### SN-13. Индекс «по status и must_be_finished_at» из ТЗ неоптимален ✅

Один составной индекс не обслуживает обе ветки `OR`-предиката. Приняты два частичных
индекса точно под предикаты claim'а (design §4): они (а) покрывают обе ветки
(BitmapOr), (б) не содержат миллионы completed-строк, т.к. частичные. Рекомендация
ТЗ фактически уточнена.

### SN-14. Латентность доставки до `interval` ✅ (компромисс)

Ticker-поллинг: задача, вставленная сразу после тика, ждёт до `interval`.
Уменьшение interval пропорционально увеличивает нагрузку пустых запросов.
v1 — ticker (простота, предсказуемая нагрузка); v2 — сигнал диспетчеру после
освобождения воркера (eager wake-up, design §12.1).

### SN-15. Exactly-once недостижим в принципе ✅ (задокументировано)

Даже с идеальным fencing сайд-эффекты обработчика (отправка письма, HTTP-вызов)
могут выполниться дважды: lease истёк → перехват → оба обработчика завершились
успешно на своих сайд-эффектах. Это фундаментальное свойство at-least-once систем
без бизнес-идемпотентности. Библиотека честно фиксирует это в контракте
(`JobHandler` docstring) и в R-1. «Точно один раз» можно получить только уровнем
выше: уникальный бизнес-ключ отправки, таблица идемпотентности и т.п.

## Часть 2. Реестр рисков (R)

| # | Риск | Вер-ть | Последствие | Митигация |
|---|---|---|---|---|
| R-1 | Двойное выполнение сайд-эффектов (at-least-once) | средняя | бизнес-инцидент (двойное письмо/платёж) | контракт идемпотентности обработчика; fencing состояния; примеры в доке; SN-15 |
| R-2 | Обработчик дольше `execution_timeout` → параллельный перехват | средняя | дубль + лишняя нагрузка | локальный `WithTimeout` на попытку; документация «таймаут = верхняя граница времени попытки»; v2 — heartbeat |
| R-3 | Обработчик игнорирует отмену ctx (утечка горутин, «зомби» дорабатывает после снятия) | средняя | ресурсные утечки, R-2 | документ контракта `JobHandler`; fencing не даст зомби испортить состояние; пример корректного обработчика |
| R-4 | Рассинхрон часов инстансов | низкая | ложные истечения lease | все временные решения в SQL через `now()` БД; app-часы только для локального таймаута (джиттер ± секунды некритичен) |
| R-5 | Поллинг нагружает OLTP-базу; БД — единая точка отказа очереди | низкая (1 запрос/interval/инстанс) | деградация основного трафика | два крошечных частичных индекса; мониторинг `pg_stat_statements`; interval — настройка; отдельная реплика не подходит (нужна запись) |
| R-6 | Рост `completed`-строк, bloat, распухшие индексы | высокая (со временем) | деградация поллинга, диск | helper `Purge` с батчами; мониторинг глубины; планирование autovacuum на таблице |
| R-7 | Ошибка финализации после успешного `Execute` (сеть мигнула) | низкая | задача выполнена, но перезапустится → дубль сайд-эффекта | ретраи финализации (3 попытки); self-heal: lease истечёт, задача перехватится; fencing защитит состояние |
| R-8 | Один медленный `task_type` занимает всех воркеров (глобальный concurrency) | высокая при смешанных нагрузках | голодание других типов | v1: документировать, поднимать concurrency/разносить типы по разным Engine; v2: per-type limits |
| R-9 | `ORDER BY ... LIMIT 1 FOR UPDATE SKIP LOCKED` вернёт пусто, если первая строка заблокирована | низкая | задержка доставки на 1 тик | безвредно (следующий тик); документировано; batch-claim в v2 снимает |
| R-10 | `RegisterHandler` из горутины параллельно со `Start` — гонка на map | низкая | паника/UB | контракт: регистрация строго до `Start`; в реализации — при `Start` map замораживается (копия в dispatcher) |
| R-11 | Паника обработчика | высокая (чужой код) | падение всего процесса воркеров | `recover` в обёртке → путь Fail (SN-7) |
| R-12 | Большие JSONB-payload (TOAST) | средняя | медленный claim, лишний I/O | документация: payload ≤ ~2KB, передавать ссылки |
| R-13 | Секреты в payload (токены, пароли) | средняя | утечка через логи/БД-доступы | документация: payload не шифруется; секреты по ссылке/ID |
| R-14 | Дублирование существующих решений (River, gue) | — | стоимость сопровождения | осознанное решение ТЗ (обучающая/встраиваемая библиотека); сравнение — design, Приложение B; при росте потребностей — миграция |
| R-15 | Долгая клиентская транзакция с `EnqueueTx` задерживает видимость задачи | низкая | задержка старта задачи | свойство outbox (изоляция), не дефект; документация: бизнес-tx должны быть короткими |

## Часть 3. Сводка изменений относительно буквального ТЗ

| Область | Буквальное ТЗ | Принято в design.md | Статус |
|---|---|---|---|
| Инкремент `attempts` | на захвате **и** на ошибке | только на захвате (SN-1) | 🔧 |
| Схема | 12 колонок | + `next_attempt_at`, `lease_token` (SN-3, SN-4) | 🔧 ждёт подтверждения |
| API постановки задач | отсутствует | `Enqueue` / `EnqueueTx` (SN-2) | 🔧 |
| `RegisterHandler` | `(string, JobHandler)` | `+ opts ...HandlerOption` → `error` (SN-6) | 🔧 |
| `Start` | без возврата | `error` (SN-6) | 🔧 |
| Индексы | «по status и must_be_finished_at» | два частичных индекса под предикат claim'а (SN-13) | ✅ уточнение |
| `execution_timeout` | per task_type | сохранено, через `WithExecutionTimeout` | ✅ |
| Поведение при панике | не определено | recover → Fail (SN-7) | ✅ уточнение |
| Незарегистрированный тип | не определено | не захватывается (SN-9) | ✅ уточнение |
| Backoff | не определено | экспоненциальный + jitter (SN-3) | 🔧 (зависит от колонки) |
| Graceful shutdown | не определено | drain + Release без сжигания попытки | ✅ уточнение |
| `Permanent`-ошибки | не определено | обёртка `dispoller.Permanent` (SN-8) | ❓ |

Все 🔧-пункты реализуемы в обратимо-совместимом виде: если владелец ТЗ отклонит
какой-либо, дизайн деградирует до Приложения A (design §13) с явной таблицей потерь
гарантий — код движка при этом не меняется, меняются только SQL-константы.
