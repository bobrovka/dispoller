## Ревью дизайна (docs/design.md + docs/spec-notes.md)

Вердикт: документация готова к передаче на реализацию. Уровень проработки
соответствует планке production-ready для небольшого проекта: контракты
(at-least-once + обязательная идемпотентность обработчика) зафиксированы честно,
граничные сценарии (fencing, перехват зависших, graceful shutdown, паники)
разобраны и покрыты планом тестирования (T-1…T-17), эксплуатация не забыта
(purge, мониторинг, роли, размер payload). Документы внутренне согласованы:
ссылки SN/R резолвятся, ревизии семантики (SN-16 → SN-18) отражены во всех
затронутых разделах единообразно.

## Верификация на живом PostgreSQL 18

Ключевые SQL из §4–§5 воспроизведены на `postgres:18` (контейнер). Всё
подтвердилось буквально:

- claim свежей pending-задачи: `processing`, `attempts+1`, `reclaims` не тронут,
  lease ровно `timeout_seconds`;
- fencing: Complete/Release по протухшему токену → 0 строк, состояние не портится;
- отложенная (`next_attempt_at` в будущем) и незарегистрированного типа задачи
  не захватываются;
- перехват истёкшего lease: `attempts+1`, `reclaims+1`;
- SN-16: перехват при `attempts = max_attempts` действительно даёт запуск сверх
  лимита (`attempts` 3→4) — ровно как задокументировано;
- SN-18: при `reclaims = max_reclaims` перехват уводит строку в `failed` без
  запуска (`lease_token = NULL`, `attempts` не тронуты, `reclaims` 10→11,
  `error_message = 'reclaim budget exhausted'`);
- SN-5: `processing` с NULL-дедлайном перехватывается defensive-веткой;
- Fail/Release/Requeue — семантика счётчиков совпадает с §7.1;
- `EXPLAIN`: `BitmapOr` по `jobs_pending_idx` + `jobs_stuck_idx`, `LockRows`
  стоит **под** `Limit` (SKIP LOCKED перебирает строки до первой свободной);
- двухсессионный тест: при удержании строки одной транзакцией конкурентный claim
  взял следующую строку за ~40 мс, не блокируясь.

## Замечания (не блокируют реализацию)

1. Стоимость claim растёт с глубиной очереди: `ORDER BY id` поверх `BitmapOr`
   заставляет отсортировать всех готовых кандидатов на каждый тик. На малых и
   средних глубинах (тысячи) это миллисекунды; при десятках тысяч готовых
   pending-строк стоит помнить (batch-claim в v2, §12.2, закроет).
2. После dead-letter `reclaims` оказывается `max_reclaims + 1`. Косметика, но
   алерт мониторинга лучше строить по `status + error_message`, а не по счётчику
   (в §10 так и сделано; строку `'reclaim budget exhausted'` при реализации
   стоит вынести в константу/документировать как контракт мониторинга).
3. `Start` при нуле зарегистрированных обработчиков молча поллит вхолостую
   (`unnest` пустого массива не матчит ничего). Рекомендую на этапе реализации
   возвращать ошибку конфигурации — тест стоит добавить в §9.1.
4. Инвариант «`must_be_finished_at IS NULL` только вне processing» заявлен
   комментарием, но не CONSTRAINT; допустимо, т.к. claim обрабатывает NULL
   defensively (SN-5).
5. Потенциальный запуск сверх `max_attempts` после аварии на последней попытке
   (SN-16) — принят сознательно, ограничен бюджетом `max_reclaims` и покрыт
   T-16; претензий нет, фиксирую как осознанный компромисс.

Итог: схема, SQL и модель конкурентности проверяемы и воспроизводимы, риски
зафиксированы с митигациями. Можно начинать реализацию.
