Создай изолированную Go-библиотеку (пакет) для обработки фоновых задач (Background Job Queue) на базе PostgreSQL. 
Библиотека должна быть полностью агностичной к бизнес-логике, переиспользуемой и работать по принципу Transactional Outbox (через DB polling).

Технический стек библиотеки:
- Язык: Go (последняя стабильная версия)
- Драйвер БД: `github.com/jackc/pgx/v5` (использовать pgxpool.Pool)
- Конкурентность: Go-рутины и каналы для управления воркерами.

Основные требования к архитектуре и логике:

1. Структура таблицы в PostgreSQL (схема `background`, таблица `jobs`):
   - id (UUID или BIGSERIAL)
   - task_type (VARCHAR/TEXT) — тип задачи
   - payload (JSONB) — параметры задачи
   - status (VARCHAR) — состояния: 'pending', 'processing', 'completed', 'failed'
   - must_be_finished_at (TIMESTAMP WITH TIME ZONE, nullable) — дедлайн текущего выполнения задачи
   - attempts (INT, default 0) — количество попыток выполнения
   - max_attempts (INT, default 3) — максимальное количество попыток
   - error_message (TEXT, nullable) — текст ошибки в случае провала
   - created_at, updated_at (TIMESTAMP WITH TIME ZONE)

2. Интерфейс обработчика (JobHandler):
   Определи интерфейс, который будут реализовывать конкретные задачи в клиентском приложении:
   type JobHandler interface {
       Execute(ctx context.Context, payload []byte) error
   }

3. Движок воркера (Worker Engine):
   - Должен инкапсулировать в себе map для регистрации хендлеров: `map[string]JobHandler`.
   - Метод `RegisterHandler(taskType string, handler JobHandler)` для привязки бизнес-логики.
   - Метод `Start(ctx context.Context, interval time.Duration, concurrency int)` — запускает бесконечный цикл (polling) с заданным интервалом. Количество одновременно обрабатываемых задач должно быть ограничено параметром `concurrency` (используй пул воркеров на горутинах или семафор на каналах).

4. Логика Polling-запроса (Критически важно):
   Напиши SQL-запрос для захвата задачи, использующий `FOR UPDATE SKIP LOCKED`. 
   Запрос должен атомарно выбирать ОДНУ задачу, которая:
   - Либо имеет статус 'pending'
   - Либо имеет статус 'processing', но текущее время `NOW() > must_be_finished_at` (это означает, что предыдущий воркер завис или упал).
   При захвате задачи статус должен меняться на 'processing', `attempts` увеличиваться на 1, а метка `must_be_finished_at` обновляться как `NOW() + execution_timeout` (сделай его настраиваемым для каждого task_type свой).

5. Жизненный цикл задачи после выполнения:
   - Если `Execute` вернул `nil`: статус меняется на 'completed'.
   - Если `Execute` вернул ошибку: увеличиваем `attempts`. Если `attempts < max_attempts`, переводим статус обратно в 'pending' (для ретрая при следующем поле), иначе — в 'failed' и записываем `error_message`.

Что конкретно нужно сгенерировать:
1. SQL-скрипт создания таблицы `background.jobs` с необходимыми индексами (например, по status и must_be_finished_at). Код, применяющий миграции не нужен (мигратор), это задача клиента.
2. Полный код Go-пакета (структуры, интерфейсы, методы регистрации и логика пула воркеров).
3. Пример кода клиентского приложения (как инициализировать библиотеку, зарегистрировать тестовый хендлер отправки email и запустить воркер).
4. Юнит- и интеграционные тесты (желательно с использованием встроенного пакета `testing`, проверкой конкурентности, конкурентного захвата задач и симуляцией падения воркера для проверки дедлайнов).

Пиши чистый код, обрабатывай все ошибки драйвера БД и контекста (ctx.Done), пиши комментарии к ключевым блокам конкурентности.
